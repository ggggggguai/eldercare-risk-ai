# 徘徊模块协作交接与职责边界

更新时间：2026-08-03

本文是徘徊模块的协作交接契约，用来回答四个问题：谁负责、必须交付什么、由谁验收、缺失后会卡住哪一步。本文不重复维护研发进度；当前完成状态以[心理健康模块 README](README.md)、[当前任务](../../tasks/README.md)和代码为准，固定算法路线与步骤以[徘徊样行为识别技术方案](plans/徘徊样行为识别技术方案.md)为准。

## 1. 使用方法

项目负责人先填写下面的姓名、计划日期和实际交付日期，再把第 5 节对应任务发给负责人。任何任务只有在“产物已交付、接收方已验收、证据路径已填写”三个条件同时满足时，才能标记完成。

| 角色 | 负责人 | 计划日期 | 实际交付日期 | 备注 |
|---|---|---|---|---|
| R1：徘徊算法负责人（你） | 待填写 | 待填写 | 待填写 | 负责徘徊识别算法与心理模块内的徘徊证据接入 |
| R2：人体检测与跟踪负责人 | 待填写 | 待填写 | 待填写 | 负责视频到人体框轨迹，不负责徘徊分类 |
| R3：业务后端与萤石接入负责人 | 待填写 | 待填写 | 待填写 | 负责设备、鉴权、直播地址、稳定人员身份和数据持久化 |
| R4：心理健康总评分与公共接口共同维护人 | 待填写 | 待填写 | 待填写 | 若该角色也是你，可填写同一姓名；公共策略仍需共同评审 |
| R5：数据采集、授权与人工复核负责人 | 待填写 | 待填写 | 待填写 | 负责数据组织、合规材料、真值和封存测试集保管 |
| R6：前端、展示与人工处置负责人 | 待填写 | 待填写 | 待填写 | 负责卡片、文案、复核页面和业务动作 |
| R7：部署、联调与比赛材料负责人 | 待填写 | 待填写 | 待填写 | 负责运行环境、演示编排和提交材料 |
| R8：项目协调与最终验收人 | 待填写 | 待填写 | 待填写 | 分配负责人、处理跨角色阻塞并签署最终验收 |

如果团队人数较少，一个人可以承担多个角色，但不能因此省略该角色的交付物和验收证据。

持久化/调度 → 风险卡片/人工复核 → 联调、部署和比赛展示

算法仓库只输出 `AlgorithmEvent(module="mental_health")`，不建立综合风险模块，也不接管家属 App、社区后台、通知、电话或工单。详细公共字段以[算法事件输出接口](../../interfaces/算法事件输出接口.md)为准。

当前心理健康模块只有离线日级 CLI，没有徘徊在线 HTTP 服务和日级定时调度。仓库中已有的直播 HTTP 接口属于跌倒风险链路，不能当作徘徊模块已完成能力。R3/R7 若要上线徘徊链路，仍需单独完成调度、服务编排和联调。

## 3. 你负责什么

### 3.1 你的必做范围

你对以下算法工作负责，并对结果的可复现性和非诊断表述负责：

1. 审核 WanderingPatterns 和 SmartCare 的安全转换结果，配合 R5 关闭人工联系表复核门槛。
2. 冻结无泄漏 split、输入契约、训练配置、随机种子和评估协议。
3. 实现轨迹 QC、短缺口处理、统一重采样、mask、无锚点形状归一化和训练统计。
4. 在同一 split 下完成手工特征 + Random Forest、纯 TCN 和唯一目标模型 `TopoWander-MPT` 的受控对照。
5. 实现语义保持增强、摄像头污染模拟、自监督预训练、校准、OOD，以及 `uncertain/unavailable/inference_error` 的分层处理。
6. 消费 R2 提供的 bbox tracklet 和 media sidecar，实现 bbox 底边中心转换、Camera QC 和离线推理；本路线不要求人体骨架。
7. 将重叠窗口合并为 `WanderingEpisode`，再形成覆盖率归一化的 `WanderingDailySummary`；这一步是你可以独立验收的徘徊算法边界。
8. 定义从 `WanderingDailySummary` 到 `WanderingDailyEvidence` 的字段适配，并在 R3 提供稳定 `person_id`、R4 确认公共评分策略后，与 R4 共同接入现有 `mental_health` 个人基线、`routine_irregularity_score` 和 `risk_factor_details`。你负责徘徊字段和实现正确性，R4 负责共享基线与风险政策。
9. 输出离线 CLI、模型 artifact、配置与哈希、算法 JSON 示例、测试、评估报告、失败案例和算法侧 Demo fixture。
10. 对算法能证明和不能证明的范围做明确说明，不把轨迹形状测试、成人脚本烟测或无真值视频写成真实老人效果或医学诊断。

### 3.2 明确不属于你的工作

除非团队另行变更责任并记录评审，你不负责：

- 申请或管理萤石账号、设备、token、开放平台权限和直播地址。
- 在业务系统中把设备、家庭成员和长期 `person_id` 绑定。
- 开发家属端、社区端、风险卡片、人工复核页面或可视化看板。
- 建设数据库、日级任务调度、消息推送、电话通知和工单流转。
- 独自组织真人拍摄、准备知情同意、保管原视频或完成全部人工真值标注。
- 新建第二套人体检测、ByteTrack、姿态模型或实时视频循环；徘徊分支优先复用上游跟踪结果。
- 把摄像头 `track_id` 当作跨视频、跨设备或跨日的稳定老人身份。
- 修改跌倒风险评分、合并两个模块的风险等级，或输出 `module` 不是 `mental_health` 的事件。
- 决定展示层的 `L1/L2` 文案、人工处置流程或比赛页面样式。
- 在没有公共接口共同评审时，单独改变 `AlgorithmEvent` 字段、心理模块风险阈值或动作映射。

你可以为以上工作提供输入契约、算法示例和排错协助，但“协助”不等于接管交付责任。

## 4. 其他角色必须做什么

### 4.1 R2：人体检测与跟踪负责人

R2 负责把可解码视频变成徘徊算法可消费的人体轨迹，不负责判断是否徘徊。

必须交付：

- 只包含 person 类的 bbox 跟踪 JSONL 样例和正式输出说明。
- 每行至少提供 `frame_id`、相对或绝对时间、`track_id`、`bbox=[x1,y1,x2,y2]` 和检测/跟踪置信度。
- 与 JSONL 配套的 media sidecar，至少包含 `source_video_id`、`source_group_id`、不含凭据的媒体引用、有限录制片段 SHA-256、宽、高、FPS、时长、采集开始时间、时区、`device_id`、`setup_id`、`stream_epoch`、坐标系、检测器版本和跟踪器版本。
- 固定摄像头状态或相机移动/变焦/云台切换标记；发生切换时不能假装轨迹连续。
- 多人场景的目标老人选择原则和 ID switch/轨迹断裂说明。
- 一段可重放的小视频、对应 tracking JSONL、sidecar 和运行命令。

验收标准：同一 `track_id` 不跨视频或 stream epoch 合并；坐标和时间合法；原视频能与轨迹逐帧对齐；不能把临时 `track_id` 命名或宣传成稳定业务 `person_id`。无限直播本身不要求预先计算整体 SHA-256，但用于开发或验收的有限录制片段必须有 hash。

### 4.2 R3：业务后端与萤石接入负责人

R3 负责平台、身份、会话和算法之外的业务闭环。

必须交付：

- 萤石账号、设备鉴权、token 生命周期和可解码直播地址的获取与刷新逻辑。
- 算法实际可消费的 MP4、文件地址或直播会话；不能只给前端播放页或不可解码链接。
- 稳定、非空的业务 `person_id`，以及必要的 `device_id`、`session_id/stream_epoch`、时区和场景元数据。
- 设备与人员绑定规则，说明断流、重连、换设备和多人场景怎样处理；重连或输入源重置后必须产生新的 `stream_epoch`。
- 日级任务由谁触发、按哪个时区执行、输入从哪里读、事件存到哪里、迟到数据和跨午夜怎样处理、失败怎样重跑。
- 以 `person_id + local_date + artifact/config version` 为基础的幂等和补算规则，防止重跑产生重复日级记录或重复事件。
- `AlgorithmEvent` 的鉴权、幂等、持久化和回调验收记录。
- 凭据安全规则：token、密码和带密钥直播地址不得写入算法日志、manifest、模型 artifact 或比赛材料。

验收标准：算法能消费实际地址或文件；跨日输入使用稳定 `person_id`；至少保存一次后端到算法再到事件回调的可复现联调记录。只播放本地 MP4 不能宣称完成萤石开放平台接入。

### 4.3 R4：心理健康总评分与公共接口共同维护人

R4 负责共享心理评分规则和对外接口的一致性。若你同时承担 R4，也必须把公共策略变更作为独立评审，而不是只在徘徊代码中修改。

必须交付：

- 确认 `WanderingDailyEvidence` 如何进入 `routine_irregularity_score` 和 `risk_factor_details`。
- 确认冷启动、低覆盖、连续异常、基线更新和缺失徘徊模态时的评分规则。
- 确认最终仍使用整数 `risk_level=0..4` 和现有 `recommended_action` 枚举。
- 确认纯摄像头等被动证据遵守现有风险等级上限，4 级仍只由现行强自评或显式紧急证据触发。
- 评审阈值、权重或动作映射变更对整个心理健康模块的影响。
- 确认徘徊证据缺失或 `unavailable` 时不会被填成正常值 0，也不会制造高风险。
- 验收最终事件只输出 `module=mental_health`，不影响跌倒模块。

验收标准：接口测试和心理评分回归测试通过；窗口和 episode 不直接输出风险等级；展示层的 `L1/L2` 字符串不得写回 `AlgorithmEvent.risk_level`。

### 4.4 R5：数据采集、授权与人工复核负责人

R5 负责“数据是否合法、标签是否可信、测试是否真正封存”，R1 负责解释算法需要什么标签并共同处理异常。

必须交付：

- 现有步骤 2 的 6 张固定种子联系表已于 2026-08-03 完成人工检查；若转换输入或抽样清单哈希变化，负责重新记录复核人、日期、结论和异常 sample ID。
- 真人采集前的授权/知情同意、脱敏编号、访问控制、保留周期和退出删除流程。
- 摄像头烟测脚本、机位/光线/场景记录、授权状态、去标识化状态和媒体 manifest。
- 开发片段与封存烟测片段的隔离清单；同一 episode 的重叠窗口不能跨集合。
- 若要报告准确率、召回率或误报率，必须提供 episode 起止时间、类别、复核人和争议处理记录。
- 原始媒体的保管位置和 SHA-256；大型视频不直接提交到代码仓库。
- 目的性困难负例，如找东西、清洁、电话踱步、重复搬运和自然连续活动。

验收标准：不存在一段视频同时用于调参和宣称无偏测试；没有人工 episode 真值时，只能报告覆盖率、轨迹断裂、拒识率和延迟，不能报告准确率、召回率或误报率。步骤 2 的公开数据联系表检查与步骤 14 的摄像头 episode 真值是两项不同工作；两者都由项目人员离线完成，不要求老人或最终用户操作标记。

### 4.5 R6：前端、展示与人工处置负责人

R6 负责把结构化算法输出变成用户能理解的页面和处置流程，不修改算法含义。

必须交付：

- 读取算法侧 Demo fixture 和 `AlgorithmEvent` 的字段映射。
- 日/周/月趋势卡片、数据覆盖率、主要证据、模型质量状态和非诊断提示。
- 将整数风险等级映射为展示文案；展示文案不能反向改变算法契约。
- `uncertain`、`unavailable`、低覆盖和数据缺失的可见提示，不显示伪精确结论。
- `manual_review` 对应的页面、人员入口和处理状态；算法仓库不实现工单。
- 空数据、断流、身份未绑定和算法版本变化时的界面状态；`insufficient_data` 必须显示为证据不足，而不是“老人正常”。

验收标准：页面能使用固定 fixture 独立演示；风险数值、证据和质量状态与原始 JSON 一致；不显示“诊断”“确诊”或未经验证的医学结论。

### 4.6 R7：部署、联调与比赛材料负责人

R7 负责把各角色的产物组合成可运行、可复现、可展示的交付包。

必须交付：

- 固定的 `eldercare-ai` 环境或等价部署镜像、硬件说明和启动脚本。
- 模型文件、配置、版本、哈希和资源需求的部署清单。
- 从输入视频到 tracking、徘徊推理、日级证据、事件和前端 fixture 的演示编排。
- 离线 Demo、真实平台联调和前端展示分别使用什么证据的说明。
- 延迟、吞吐、内存、失败重试和长时运行记录。
- 比赛提交材料、演示录像和答辩口径；任何能力声明都必须能追溯到对应证据。

验收标准：在一台干净目标机器上按文档重放成功；最终 Demo 只加载冻结的目标模型，不把 RF/TCN 对照模型包装成部署模型；本地回放、萤石联调和真实老人验证三种证据不混写。

### 4.7 R8：项目协调与最终验收人

R8 不代替各角色开发，但必须确保每项工作真的有人负责。

必须交付：

- 填完第 1 节的姓名和日期，不允许保留“大家共同负责”。
- 每周核对第 5 节交接单，明确 `未开始/进行中/待验收/已验收/阻塞`。
- 对跨角色接口变更指定评审人，记录结论和生效版本。
- 任何阻塞超过约定日期时重新分配人员或调整计划，不默认转给 R1。
- 在最终演示前组织一次端到端验收并签字。

| 时间点 | 你可以先做什么 | 在继续前必须收到什么 | 缺失时怎么办 |

## 7. 接口责任的硬边界

### 7.1 `track_id` 和 `person_id`

- R2 生成的 `track_id` 只负责一个视频或 stream epoch 内的短时关联。
- R3 负责提供跨设备、跨视频、跨日稳定的业务 `person_id`。
- R1 负责在缺少稳定 `person_id` 时阻止日级个人基线写入，而不是猜测身份。
- 多人身份不确定时，可以保存 track-level 工程结果，但不能生成某位老人的跨日心理风险事件。

### 7.2 摄像头轨迹和训练轨迹

- R2 提供原始 bbox 与 media sidecar。
- R1 取 bbox 底边中心并归一化到 `[0,1]^2`，再做无锚点形状归一化、质量控制和拒识。
- 不用人体骨架，不要求用户贴锚点或标房间地图。
- 这一路线只能近似对齐轨迹形状，不能把图像距离解释成真实米数，也不能自动恢复跨房间身份。
- 相机移动、长遮挡、严重 ID switch 和多平面场景必须进入 `unavailable/uncertain` 或切段，不得硬分类。

### 7.3 风险等级和动作

- `WanderingWindowResult`、`WanderingEpisode` 和基线前的日级摘要都不含最终风险等级。
- R1 输出徘徊证据；R1 与 R4 共同维护它进入心理评分的映射。
- 只有心理健康日级评分管线产生数字 `risk_level=0..4` 和标准动作枚举。
- R6 可以把数字映射为 `L1/L2` 等展示文案，但不能修改算法事件原值。

### 7.4 实拍和效果指标

- 早期公开轨迹模型开发不要求实拍。
- 比赛最终交付前需要授权固定摄像头烟测，由 R5 组织、R1 运行算法、R2 排查跟踪、R7 归档证据。
- 无人工 episode 真值时，只报告覆盖率、轨迹碎片、拒识率、吞吐和延迟。
- 有人工起止时间和标签后，才可以报告 episode 级准确率、召回率和误报率。
- 同一段视频不能既用于调参，又作为封存测试证明。
