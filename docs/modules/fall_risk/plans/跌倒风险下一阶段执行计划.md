# 跌倒风险实时链路与算法语义质量冲刺计划

更新时间：2026-07-24

## 文档定位

本文档是跌倒风险模块的实时链路与算法语义质量冲刺计划，目标是把“视频帧进入算法”到“事件生成、回调投递和会话结束”的运行行为做稳定、可观测、可恢复，并证明实时化改造没有改变检测、跟踪、姿态、质量控制、时序分支、融合和事件状态的语义。

本阶段不验收数据集解锁、监督训练、模型替换、正式事件效果、个体基线或创新消融。规则评分和现有模型接口继续作为运行输入；没有正式真值时，事件数量、案例和回放结果只能用于工程回归和算法语义不退化检查，不能写成泛化效果或临床结论。

当前实现中的主要工程事实：

- `process_frame` 当前在推理路径内直接执行回调发送，网络重试和 `sleep` 可能阻塞取帧与推理。
- 回调发送当前每次生成新的随机 `event_id`，无法保证重试和重复处理复用同一事件标识。
- 会话重连和主目标丢失已有窗口重置基础，但需要验证轨迹、特征、事件状态和投递状态是否全部按会话边界清理。
- 当前主链仍以规则 fallback 为主，本阶段不把 fallback 替换成新模型。
- 当前实时推理会按 `max_inference_fps` 主动跳过输入帧；姿态插值、平滑和时序模型仍有按帧数处理的逻辑，丢帧可能改变算法语义。
- 当前特征装配以全局平均关键点质量判断可用性，并将部分无输出分支写成 `0.0`；需要改成分支级三态可用性契约，避免“不可用”被融合为“低风险”。

## 算法链路质量契约

本阶段固定以下链路，不允许通过跳过中间层直接生成最终风险：

```text
视频帧
  -> 检测与跟踪
  -> 主目标绑定与姿态关键点
  -> 关键点质量控制与时序平滑
  -> 时间规范化、有效采样与窗口构建
  -> 步态 / 坐站 / 近跌倒 / 跌倒状态 / 个体基线
  -> 风险融合与规则安全覆盖
  -> 算法过程、风险事件和投递状态
```

每一层必须定义输入、输出、源时间字段、有效性条件、不可用原因、重置条件、版本指纹和下游消费者。实时线程、队列和回调属于承载机制，不能改变上述层的输入输出语义。

## 本阶段目标

1. 保证取帧、推理、事件状态和回调投递相互隔离，回调故障不得阻塞推理。
2. 保证所有延迟使用正确的源视频时间语义，并能区分帧丢弃、排队等待、推理耗时和回调耗时。
3. 保证断流、重连、更新直播地址、时间倒退、主目标丢失和会话停止不会让旧轨迹、旧窗口或旧推理状态影响新 epoch；已生成事件保留原 epoch 和投递上下文。
4. 保证事件投递具备稳定 `event_id`、有限重试、幂等重放、队列满处理和最终失败可观测性。
5. 在固定硬件和固定故障注入集上形成可重复的运行报告、原始日志和版本指纹。
6. 在没有正式真值的前提下，通过固定回放和变形测试证明实时化改造不会静默改变分支可用性、时间窗、状态边和事件关联。

## 明确不纳入本阶段

- 新数据源、补标、正式 split、冻结测试集和监督训练。
- 步态、坐站、近跌倒或融合模型的效果比较与主路径替换。
- 个体基线长期有效性、正式事件 Precision/Recall/F1、临床或泛化结论。
- 任何把回放事件数量或链路稳定性写成模型准确率、泛化能力或临床有效性的结论。
- 跨摄像头身份合并、视觉 ReID 和业务身份管理。
- 家属端、社区后台、消息推送、工单和人工处置流程。

上述事项仍按模块 README、任务清单和数据阻塞报告管理，不作为本阶段延期或完成的依据。

## 执行原则

1. **先建立运行基线，再改线程和队列。** 每项改动必须保存代码、配置、环境、输入和原始运行日志。
2. **源时间和处理时间分开。** 不用处理 FPS 代替端到端延迟，不用本机时间覆盖源 PTS。
3. **有界优先。** 队列、缓存、重试、证据片段和日志都必须有容量或 TTL，禁止无界增长。
4. **状态按会话边界隔离。** 每次重连、地址更新和停止都产生可追踪的 `stream_epoch` 或等价边界。
5. **失败可见但不拖垮主链。** 回调失败、帧丢弃、目标不确定和质量不足必须记录原因；不能用静默清空掩盖失败。
6. **事件幂等。** 同一事件版本的重试和重放复用 `event_id`；升级或恢复生成新的不可变事件版本，并通过 `episode_id` 关联。
7. **采样语义守恒。** 丢帧、降采样和推理变慢必须显式进入有效采样、`gap`、重采样或质量 mask；不能把不规则时序当作等间隔连续帧。
8. **不可用显式化。** 每个算法分支使用 `valid score`、`unavailable`、`inference_error` 三态，禁止用 `0.0` 代替缺失、质量不足或模型失败。
9. **时钟分域。** 源 PTS 用于动作时间语义，本机单调时钟用于等待和耗时，对外时间必须有明确的 PTS 到绝对时间映射。
10. **事实与状态分离。** 推理状态随 epoch 重置；已生成事件是带原 epoch 的不可变事实，不因重连而静默删除。

## 运行质量指标

所有正式运行前冻结一份 `runtime_acceptance.yaml`，其中记录硬件、视频输入、采样率、队列容量、延迟预算、连续运行时长和故障注入次数。报告至少包含：

### 延迟与积压

- 源 PTS 到取帧、推理开始、推理结束、事件生成和回调成功确认的时间戳。
- 解码、检测、跟踪、目标选择、姿态、质量控制、时间规范化、步态、坐站、近跌倒、跌倒状态、个体基线、融合、事件序列化和投递分段的 P50/P95。
- 端到端事件延迟、最新帧等待时间、队列深度、最大帧龄和积压持续时间。
- 丢帧数量及原因，区分主动丢弃旧帧、解码失败、推理失败和队列满。
- 有效采样 FPS、相邻有效观测的 P50/P95/最大 `gap`、窗口覆盖时长、窗口有效帧比例和每个分支的输入帧数。

### 资源与稳定性

- 固定硬件上的有效处理 FPS、CPU/GPU、内存峰值和连续运行时长。
- 线程数、队列容量、outbox 未投递数量、重试次数和最终失败数量。
- 运行期间不能出现无界队列增长、内存持续增长、死锁、未捕获线程异常或停止无法返回。

### 边界与状态

- 断流、重连、地址更新、会话停止和时间倒退后的 `stream_epoch`、轨迹、窗口、状态和 outbox 清理结果。
- 主目标短时丢失、目标重新出现、多人交叉和新目标接替时的选择、降级和重置原因。
- 每个分支的 `valid / unavailable / inference_error` 数量、质量门禁、fallback 原因、输入窗口和输出版本。
- 同一过程的 `episode_id`、事件版本 `event_id`、升级关系、重复回调和最终投递状态。
- 事件时间、证据窗口和状态时间线使用的时钟域；不把本机处理时间写入源动作时间。

### 算法语义回归

- 固定输入在无改动基线与候选版本之间的分支可用性、窗口起止、状态边和事件关联对照。
- 允许范围内处理变慢、丢帧、队列切换和回调故障时，输出变化必须落在冻结的时间/分数容差内；超过采样或质量门槛时必须转为不可用或降级。
- 变形回放不能新增跨目标、跨 epoch 或跨时间边界的事件；同一过程不得被拆成无法关联的多个事件。

## 阶段 0：运行指纹与基线

### 0.1 基线输入

建立最小但固定的运行集，不要求其能支撑正式算法效果，但必须覆盖算法语义边界：

- 单人正常行走、正常坐站和一段静止画面。
- 快速下沉、近跌倒后恢复、疑似跌倒后长时间静止，以及正常睡眠/静止等易混淆片段。
- 目标短时丢失、多人进入和交叉遮挡。
- 低光、局部遮挡、关键点缺失、时间间隔异常、短时缺帧、降采样、断流后重连和直播地址更新。
- 回调成功、超时、非 2xx、连接失败、重试和队列满。

每个输入记录内容 hash、时长、源 FPS、场景、是否真实直播、是否故障注入和预期行为不变量。

为每个固定输入保存一份 golden replay，至少包括检测/跟踪轨迹、主目标选择、质量摘要、各分支可用性与分数、融合结果、状态时间线、`episode_id` 和事件版本。golden 不是准确率证据，只用于检测实时化改造造成的语义变化。

### 0.2 运行指纹

每次基线和候选运行至少保存：

- Git revision 或工作树标识、最终配置 hash、环境版本和启动命令。
- 姿态后端、跟踪器、规则/模型版本、队列和超时参数。
- 源 PTS、接收时间、推理完成时间、事件生成时间和回调确认时间。
- 结构化运行日志、事件 JSON、状态时间线、性能摘要和失败日志。

### 0.3 退出条件

- 同一版本、配置和输入重复运行时，事件顺序、状态边界和关键计数一致；允许的非确定性必须显式列出。
- 每个输入都有可自动检查的行为不变量，不以进程退出码为唯一通过条件。
- 无故障候选版本与 golden replay 的逐层输出差异在冻结容差内；不可比的 GPU/跟踪器非确定性必须定义比较层级和容差，不能笼统标记为“允许”。
- 形成第一版 `runtime_acceptance.yaml`、基线报告和已知失败清单。

## 阶段 1：取帧、时间和最新帧策略

### 1.1 时间契约

- 明确并分开 `source_pts_sec`、`received_monotonic_sec`、`inference_monotonic_sec`、`callback_confirmed_monotonic_sec` 和对外事件绝对时间的字段、单位与来源。
- 动作窗口、速度、持续时间、证据区间和事件发生时间使用源 PTS；排队等待、处理耗时、停止预算和网络超时使用本机单调时钟。
- 只有在存在源采集绝对时间或冻结的 PTS 到绝对时间映射时，才报告源 PTS 到接收时间的实际延迟；否则报告媒体时间积压和本机处理耗时，不混称为端到端延迟。
- 源时间倒退、重复时间戳、异常间隔和重连产生显式时间边界，不跨边界拼接窗口；跨 epoch 的对外时间线不能假设 PTS 连续。

### 1.2 最新帧队列

- 取帧线程与推理线程解耦，使用有界 latest-frame 队列；队列满时按明确策略丢弃旧帧，并记录丢弃原因、源 PTS、帧龄和丢弃造成的时间 gap。
- 对步态、坐站、近跌倒、跌倒状态和时序模型分别冻结最低有效采样率、最大相邻 gap、窗口时长和最小有效帧比例。latest-frame 只解决积压，不自动保证时序输入有效。
- 明确一种或多种时序策略：按源时间重采样、显式 gap/质量 mask、分支拒识，或为事件片段保留受保护帧。超过门槛时输出 `unavailable`/降级原因，不继续按等间隔帧评分。
- 推理线程不能因处理慢而持续消费过期帧；报告最大帧龄、有效采样率和端到端积压，而不是只报告处理 FPS。
- 停止、异常和重连时队列必须可排空或显式丢弃，不能把旧帧带入新 `stream_epoch`。

### 1.3 退出条件

- 人工注入处理变慢时，队列深度和帧龄保持有界；不出现无界积压。
- 人工注入处理变慢和丢帧时，仍能检查每个分支的有效采样率、最大 gap、窗口覆盖和可用性状态。
- 时间倒退和重连测试中，窗口不跨边界；同一 epoch 内源时间线保持单调，跨 epoch 事件通过 epoch 和绝对时间映射区分。
- 推理线程不会因为取帧阻塞或帧队列排空而无法停止。

## 阶段 2：推理窗口、目标和会话边界

### 2.1 推理与窗口

- 检测、跟踪、目标选择、姿态、质量控制、时间规范化、步态、坐站、近跌倒、跌倒状态、个体基线和融合分别计时，并记录输入帧数、有效帧数、缺失比例、最大 gap、窗口起止时间和输出版本。
- 每个分支分别定义质量门禁：核心关键点覆盖、分支关键点覆盖、有效帧比例、窗口覆盖时长、采样率和可接受 gap 不能用一个全局平均质量分替代。
- 每个分支输出 `valid score`、`unavailable` 或 `inference_error`；融合必须消费显式可用性 mask，缺失分支不能默认为零风险。
- 对固定窗口做缓存或增量计算，避免每次分析全量重算；任何优化都必须与 golden replay 对照逐层输出、时间语义、状态边和资源峰值。
- 低质量、无目标、模型异常、窗口不足、采样不足和身份不确定必须输出结构化原因，不把异常输入转换成正常风险。

### 2.2 目标选择与隔离

- `person_id` 是业务侧对专属视频流的先验，不是视觉识别结论；`track_id` 只作为单路视频证据，本阶段不做跨摄像头身份合并。
- 目标选择显式区分 `unbound`、`bound`、`ambiguous` 和 `lost`；单人不等于已完成身份验证，多人或目标不唯一时进入降级状态，不自动把新轨迹静默绑定到原人员。
- 冻结短时丢失后的恢复条件、轨迹切换条件、多人交叉处理和新目标接替规则；不满足同一目标证据时，旧窗口和个人基线不能迁移到新轨迹。
- 主目标丢失超过配置 TTL、目标接替、多人交叉无法判定或跟踪器重置时，隔离旧窗口并记录原因；重新绑定必须从新的有效窗口开始。

### 2.3 `stream_epoch`

重连、地址更新和会话重启必须创建新的 `stream_epoch`，并原子处理：

- tracker 的主轨迹和丢失计时；
- 姿态、特征、事件状态和窗口缓存；
- 未完成的算法过程、窗口和状态；
- 新 epoch 的输入队列和生产上下文；
- 未完成过程的清理原因和诊断记录。

已经生成的事件不属于可静默清除的窗口状态：事件保留原 `stream_epoch`、不可变载荷和投递上下文，重连只切换推理生产 epoch，不取消旧事件的有限投递。

### 2.4 退出条件

- 断流、地址更新和停止后，旧帧、旧轨迹、旧窗口和旧状态不会影响新 epoch。
- 目标丢失、目标重现和多人交叉均有稳定、可解释的绑定、恢复或降级结果。
- 新旧 epoch 之间不存在轨迹、姿态、个人基线和未完成算法状态泄漏；已生成事件仍可按原 epoch 查询和投递。
- 会话停止在有帧积压、有回调重试和有未完成事件时仍能在配置的停止预算内返回，并报告排空结果。

## 阶段 3：事件状态与异步 outbox

### 3.1 事件状态

本阶段只验收运行状态的一致性，不宣称状态识别效果。算法过程状态、风险事件版本和投递状态分开记录。

算法过程状态至少记录：

- `idle`、`suspected`、`confirmed_static`、`recovered`、`unresolved` 和技术失效/清理原因。
- 状态进入时间、来源 epoch、峰值时间、最后观测时间、TTL 和清理原因。
- 同一过程的稳定 `episode_id`；`confirmed_static` 只表示静止条件满足，不等同于医学或人工确认跌倒。

每条状态边必须有明确的触发条件、超时、输出动作、清理动作和输入质量门禁；非法转移、重复进入、跨 epoch 转移和由 `unavailable` 伪造的状态都要能自动检测。

风险事件版本使用 `episode_id + event_id` 关联：同一过程的首次事件、升级和恢复更新生成不同的不可变事件版本；同一事件版本的重试和重放复用同一 `event_id`。

投递状态单独记录 `pending`、`retrying`、`delivered`、`failed` 和停止排空结果，不能把投递失败改写为算法过程失败。

### 3.2 有界异步 outbox

- `process_frame` 只负责生成不可变事件版本并尝试写入有界 outbox，不执行网络请求、重试等待或阻塞式证据生成。
- outbox 记录 `event_id`、`episode_id`、`session_id`、`stream_epoch`、事件状态、首次生成时间、源事件时间、证据窗口、重试次数、最后错误和投递状态。
- 网络超时、非 2xx、连接失败和进程停止都使用有限重试；重试复用同一 `event_id`。
- 队列满时按事件等级和事件版本策略处理，必须记录丢弃或降级计数；不能静默覆盖紧急事件，也不能删除唯一的 episode 终止信息。
- 投递成功、最终失败和停止排空结果均可查询或写入结构化诊断。

### 3.3 退出条件

- 注入回调延迟和失败时，`process_frame` 的延迟不随网络等待线性增长；主推理仍可持续运行。
- 同一事件版本重试和重放不会产生新的 `event_id`；升级、恢复和状态更新使用新的事件版本并与原 `episode_id` 关联。
- outbox 达到容量上限时行为确定，停止时不会无限等待或丢失未记录的状态。

## 阶段 4：故障注入、观测和真实链路

### 4.1 必测故障

| 类别 | 注入 | 必须观察 |
|---|---|---|
| 输入 | 缺帧、重复 PTS、时间倒退、解码异常 | 时间边界、窗口清理、错误原因 |
| 跟踪 | 主目标丢失、多人交叉、新目标进入 | 目标选择、降级、epoch 和旧状态隔离 |
| 流 | 断流、重连、地址更新、停止 | 资源释放、重连耗时、状态清理 |
| 回调 | 超时、连接失败、非 2xx、慢响应 | 推理延迟、重试、outbox、最终失败 |
| 资源 | 姿态变慢、CPU 受限、队列满 | 帧龄、丢帧、内存、停止预算 |

所有故障注入都要同时检查运行指标和算法语义：分支可用性、窗口边界、质量 mask、风险分数来源、状态边和事件关联不能只通过“进程仍在运行”判定。

### 4.2 固定回放与变形测试

对每个 golden replay 至少生成以下候选：

- 无故障重复运行，用于检查非确定性和逐层输出容差；
- 注入推理延迟、有限丢帧和队列切换，用于检查采样门禁、窗口语义和降级结果；
- 在非事件边界断流/重连，用于检查新 epoch 的独立性；
- 在事件生成后断流/重连，用于检查旧事件事实和投递上下文不丢失；
- 回调超时、失败和恢复，用于检查上游特征、状态和事件版本不受网络阻塞影响。

每个变形测试必须声明允许的变化：例如处理时间、帧龄、有效帧数和投递状态可以变化；源动作时间、epoch 边界、质量不可用语义、episode 关联和超出门槛后的降级结果不能静默变化。

### 4.3 真实萤石链路

真实设备或开放平台直播只用于验证链路连通性和运行稳定性，必须区分真实直播、同链路录像和离线回放。验收记录至少包含启动、持续运行、回调、地址更新、重连和停止；不把演示事件当作算法准确率证据。

### 4.4 观测与脱敏

- 日志、配置快照和报告不记录 token、完整直播地址或未经授权的身份信息。
- 运行诊断能按 `session_id`、`stream_epoch`、`episode_id`、`event_id` 关联取帧、推理、状态和回调日志。
- 故障报告保留原始错误、重试链、队列计数和清理原因，不只保留最终“失败”。

## 阶段总验收

候选版本只有同时满足以下条件才能作为实时演示版本：

1. `runtime_acceptance.yaml`、固定输入、硬件、配置和运行命令已冻结。
2. 链路每一层的延迟、输入输出计数、质量门禁、可用性状态、队列、资源和失败指标均有原始记录。
3. 时钟域、有效采样率、最大 gap、窗口覆盖和分支降级规则已冻结；不规则时序不能被当作正常等间隔输入。
4. 无故障候选与 golden replay 的逐层输出、窗口边界、状态边、`episode_id` 和事件版本在冻结容差内。
5. 所有必测故障均通过算法语义不变量检查，或将失败明确记录为阻塞项；不得以平均 FPS 掩盖采样退化、质量误判或回调阻塞。
6. 重连、地址更新、停止和 epoch 切换没有轨迹、窗口、状态或个人基线泄漏；已生成事件保留原 epoch、不可变载荷和有限投递上下文。
7. 固定输入重复运行可复现状态边界、事件关联和关键计数；不可复现项有明确比较层级、容差和原因说明。
8. 真实直播、录像回放和离线输入在报告中明确区分，材料不宣称本阶段未验证的模型效果。

## 交付物

本阶段只要求生成以下算法侧产物：

- `runtime_acceptance.yaml` 及其 hash。
- 完整链路输入/输出/时钟/质量/重置契约和分支可用性矩阵。
- 固定输入 golden replay、变形回放索引及逐层差异报告。
- 实时链路基线与候选版本对照报告。
- 分段延迟、有效采样率、最大 gap、窗口覆盖、帧龄、丢帧、队列、资源和连续运行报告。
- 故障注入矩阵、原始日志、状态时间线和清理原因。
- 每个分支的质量门禁、`valid / unavailable / inference_error`、fallback 和融合 mask 记录。
- outbox 投递、`episode_id/event_id` 关联、重试、幂等、队列满和停止排空记录。
- 真实萤石联调记录、版本指纹和同链路录像索引。

数据真值、监督模型、正式算法指标和创新消融继续写入各自的任务、评估和实验文档，不在本计划中重复维护。

## 近期执行顺序

1. 先冻结完整链路契约、时钟矩阵、分支质量门禁和 golden replay，补齐运行指纹与分段耗时，跑出无改动基线。
2. 再实现 latest-frame 队列、有效采样/gap 处理、停止和 epoch 边界，完成输入、目标和重连变形回放。
3. 再实现固定窗口缓存或增量计算，并完成逐层 golden 等价测试；不通过等价门禁不能替换原路径。
4. 再把同步 callback 改为有界异步 outbox，完成 episode/event 关联、超时、非 2xx、重试和幂等测试。
5. 最后在固定硬件上跑连续运行、弱网、真实直播和停止验收，并冻结报告。
