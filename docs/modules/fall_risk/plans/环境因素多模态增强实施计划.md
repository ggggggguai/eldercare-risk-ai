# 环境因素多模态增强实施计划

更新时间：2026-07-29

> 本文是待实施计划，不是当前能力说明。当前主链已经具备视频跟踪、姿态、行为分支、风险融合和三态诊断；环境设备接入、环境交互特征和 assist 融合尚未实现。实施状态仍以 [跌倒风险模块 README](../README.md)和[当前任务](../../../tasks/README.md)为准。

目标架构和稳定接口以 [环境因素多模态增强设计方案](环境因素多模态增强设计方案.md)为准；本文只说明实施顺序、实验门禁和验收方式。

## 1. 一页结论

本计划解决一个具体问题：现有 `scene_risk_score` 只能表达浴室、床边等静态场景先验，不能反映“此刻光线变暗”或“探头附近此刻有水”这类短时环境变化。

计划通过 ESP32-S3 接入 TSL2591 照度传感器和水浸探头，在现有人体行为分支之后生成“行为风险 × 环境暴露”交互特征。环境信号先以 `shadow` 模式连续记录，只有在配对数据、固定划分和冻结评估证明有效后，才允许通过 `assist` 模式有限调整跌倒模块内部风险分。

完整推进顺序如下：

```text
冻结数据与配置契约
  -> 打通环境上报和有界缓存
  -> 按视频帧接收时间完成因果对齐
  -> 计算弱光与水浸区域交互特征
  -> shadow 连续采集与数据质量验证
  -> 离线评估 assist
  -> 通过门禁后才允许受控启用
```

任何阶段不满足退出条件，都停留在 `disabled` 或 `shadow`，不能为了演示直接打开 `assist`。

## 2. 目标、边界与硬约束

### 2.1 本计划交付什么

- 定义可版本化的环境上报 schema、设备绑定和标定配置；
- 在服务进程中提供鉴权接口和线程安全、有界的环境记录缓存；
- 将环境记录与当前视频帧按服务端单调时间做因果对齐；
- 生成弱光、水浸探头区域暴露和人-环境交互特征；
- 在 `FeatureSnapshot` 中记录完整诊断，并为 shadow 实验连续落盘；
- 完成基线与 assist 的配对实验、消融评估和准入判断；
- assist 通过门禁后，以默认关闭的配置接入 `FallRiskPipeline`。

### 2.2 本计划不做什么

- 不让照度或水浸信号绕过人体检测、姿态和行为分支直接告警；
- 不把一个水浸探头解释成整个房间或整个地面湿滑；
- 不用 LED 的控制值代替 TSL2591 的实测照度；
- 不根据环境信号识别人，也不解决多人身份绑定问题；
- 不实现设备注册、远程配置、固件升级、账号权限或业务告警流程；
- 不新增综合风险模块，最终仍只输出 `module=fall_risk`；
- 不用计划中的公式或模拟采集结果宣称真实老人跌倒风险效果。

ESP32 固件、传感器安装和局域网配置是本计划的外部集成依赖。本仓库负责算法服务的接收契约、运行时处理、实验工具和评估，不扩展为物联网设备管理系统。

### 2.3 不得破坏的系统不变量

| 不变量 | 具体要求 |
|---|---|
| 缺失不等于低风险 | 环境缺失、过期、故障或计算失败必须是 `unavailable/inference_error`，不能填成有效 `0.0` |
| 环境不能独立告警 | 没有至少一个有效行为分支时，不计算环境交互分，也不提高风险等级 |
| 4 级只由原强触发产生 | 环境分支不能产生或伪造 `fall_or_long_static`，不能把非 4 级事件提升到 4 级 |
| shadow 不改变决策语义 | `risk_score`、`risk_level`、`confidence`、`trigger_event`、顶层 `risk_factors`、`recommended_action` 和 episode 转移与基线完全一致 |
| 默认行为不变 | `environment.mode=disabled` 时不要求设备存在，现有输入、输出和性能路径保持兼容 |
| 模块边界不变 | 环境只参与跌倒模块内部融合，不读取或修改心理健康分数 |

## 3. 运行模式与端到端链路

### 3.1 三种运行模式

| 模式 | 环境数据接收 | 特征与诊断 | 影响风险分 | 用途 |
|---|---:|---:|---:|---|
| `disabled` | 否 | 否 | 否 | 默认配置和无硬件部署 |
| `shadow` | 是 | 是，并连续写实验日志 | 否 | 数据质量、对齐、误触发和性能验证 |
| `assist` | 是 | 是 | 是，且受行为门禁和等级上限约束 | 仅限通过冻结评估后的受控实验或部署 |

使用单一 `mode` 字段，避免 `enabled=false + mode=assist` 这类冲突组合。配置加载时只接受上述三种枚举；shadow 缺少日志路径时应启动失败；assist 缺少权重、标定版本、日志路径或准入报告版本时也应启动失败，而不是静默回退。

### 3.2 端到端数据流

```text
环境设备
  ESP32-S3 -> POST /v1/environment/readings -> EnvironmentStore
                                                   |
                                                   | 按 camera binding 和
                                                   | frame_received_monotonic 取值
                                                   v
视频主链
  视频帧 -> StreamingPoseTracker -> FeatureAssembler
                                      |  步态 / 坐站 / 近跌倒 / 跌倒状态
                                      |  弱光 / 水浸探头区域暴露
                                      v
                              environment interaction
                                      |
                         disabled / shadow / assist
                                      v
                              FallRiskPipeline
                                      v
                     module=fall_risk AlgorithmEvent
```

环境分支位于姿态质量控制和行为分析之后、最终风险融合之前。检测、跟踪、姿态质量控制、跌倒强触发和 episode 状态机的原有职责不变。首轮不修改会话启动请求，仍使用会话 `device_id` 查找摄像头与环境设备的配置绑定。

## 4. 环境输入契约

### 4.1 设备上报

ESP32-S3 以 1～2 Hz 读取 TSL2591；水浸探头在设备端防抖后定期随照度上报，并在状态变化时立即补报。建议的 v1 请求如下：

```json
{
  "schema_version": "1.0",
  "device_id": "env-node-01",
  "boot_id": "01J4DEVICEBOOT",
  "boot_started_at": "2026-07-29T09:58:02.100+08:00",
  "sequence": 1842,
  "observed_at": "2026-07-29T10:20:31.420+08:00",
  "clock_status": "synced",
  "illumination_lux": 18.6,
  "illumination_status": "ok",
  "water_probes": {
    "bathroom_door": {
      "state": "dry",
      "sensor_status": "ok"
    }
  },
  "sensor_status": "ok"
}
```

关键字段语义：

| 字段 | 规则 |
|---|---|
| `schema_version` | 首版固定为 `1.0`，未知主版本拒绝接收 |
| `device_id` | 环境节点稳定 ID，必须存在于服务配置 |
| `boot_id` | 每次设备启动生成的新 ID，用于区分重启后的 sequence 归零 |
| `boot_started_at` | 当前 boot 的带时区启动时间；用于判断新旧 boot，当前 boot 内保持不变 |
| `sequence` | 同一 `device_id + boot_id` 内严格递增；重复值幂等，回退值记为乱序并拒绝写入 |
| `observed_at` | 设备 UTC/带时区时间，用于接收门禁、漂移诊断和离线复现 |
| `clock_status` | 至少支持 `synced/unsynced`；未同步记录不能作为有效环境输入 |
| `illumination_lux` | 照度通道正常时为有限非负数；通道故障时为 `null`，不得伪造正常数值 |
| `illumination_status` | 照度通道状态，至少支持 `ok/degraded/fault` |
| `water_probes` | 只允许配置中已知的探头 ID；`state` 为 `dry/water/unknown`，故障时必须为 `unknown` |
| `sensor_status` | 设备总体状态，至少支持 `ok/degraded/fault` |

服务接收后补充 `received_at` 和 `received_monotonic_sec`，并计算 `transport_age_sec = received_at - observed_at`。`POST /v1/environment/readings` 复用现有 `ALGORITHM_API_TOKEN` Bearer 鉴权；非法 schema、未知设备、状态与数值矛盾、非有限 lux 和超限请求返回 4xx，不进入缓存。时钟未同步、设备时间超前或传输年龄超限的合法记录可以进入诊断缓存，但不能作为有效环境输入。明确标记传感器故障的记录同理，只将对应传感通道标记为 `unavailable`。

接口结果必须可区分：首次接收返回 `202 accepted`，同一 `device_id + boot_id + sequence` 的完全相同请求返回 `200 duplicate`，同键不同载荷、旧 boot 迟到包和当前 boot 的 sequence 回退返回 409，schema、设备或字段非法返回 422。不同 `boot_id` 只有在 `boot_started_at` 晚于当前 active boot 且设备时钟健康时才能切换为新 boot。`disabled` 模式不写缓存并返回 503。若接口语义需要调整，必须先同步修改设计方案和接口文档，不能只改实现。

`boot_id` 不能省略。否则设备重启后 sequence 从零开始，服务无法区分合法重启与旧包重放。

### 4.2 进程内缓存

`EnvironmentStore` 按环境设备保存固定容量的短时环形缓冲，而不只保存一个“最新值”。它至少负责：

- 以 `device_id + boot_id + sequence` 去重；
- 每个设备只维护一个 active boot；切换到新 boot 后，拒绝旧 boot 的所有迟到记录；
- 拒绝 active boot 内的 sequence 回退；同键不同载荷视为冲突而不是幂等；
- 支持按服务端单调时间查询不晚于指定视频帧的最新记录；
- 提供接收数、重复数、乱序数、传感器故障数和缓存淘汰数；非法请求数由 API 层单独统计；
- 使用线程锁保护 HTTP 写入线程与视频推理线程的并发访问；
- 进程重启后从空缓存开始，不持久化或复用旧单调时间。

固定容量是运行时保护，不是实验数据保存方案。shadow 的连续记录由独立实验日志承担，见第 7.3 节。

### 4.3 设备绑定与标定配置

建议配置如下：

```yaml
environment:
  mode: disabled
  max_age_sec: 3.0
  max_transport_age_sec: 2.0
  max_future_skew_sec: 0.5
  store_capacity_per_device: 256
  shadow_log_path: null
  roi_window_frames: 3
  roi_min_usable_frames: 2
  roi_min_hits: 2
  roi_max_span_sec: 1.0
  camera_bindings:
    ezviz_cam_001:
      environment_device_id: env-node-01
      calibration:
        severe_low_lux: null
        normal_lux: null
        version: null
      water_probe_rois:
        bathroom_door:
          version: bathroom-door-roi-v1
          polygon:
            - [0.10, 0.72]
            - [0.42, 0.70]
            - [0.47, 0.98]
            - [0.05, 0.98]
  assist:
    weight: null
    min_behavior_anchor: null
    policy_version: null
    acceptance_report: null
```

lux 阈值必须按传感器安装位置现场试采后冻结，且满足 `0 <= severe_low_lux < normal_lux`；它们不是通用照明安全标准。ROI 使用归一化图像坐标，并绑定摄像头安装位和版本。摄像头移动、变焦或重新安装后，旧 ROI 立即失效，必须重新标定。

## 5. 在线时间对齐

视频动作使用源 PTS，环境设备提供 UTC；这两个时钟不能直接相减。服务先用设备时间识别明显滞留或未来时间的记录，再用服务进程单调时间完成在线因果对齐：

1. 视频帧进入 `LatestFrameBuffer` 时记录 `frame_received_monotonic_sec`。
2. 环境请求被服务接受时记录 `environment_received_monotonic_sec`。
3. 处理主目标姿态时，从绑定设备的环形缓存中选择满足 `environment_received_monotonic_sec <= frame_received_monotonic_sec` 的最新记录。
4. 计算 `snapshot_age_sec = frame_received_monotonic_sec - environment_received_monotonic_sec`。
5. 仅当 `0 <= snapshot_age_sec <= max_age_sec` 时，快照才可能为 `valid`；无因果记录或记录过期时均为 `unavailable`。

这条规则避免视频帧在队列中等待时错误使用“帧到达之后才收到”的环境记录。`observed_at` 不参与视频窗口排序，但 `clock_status`、`max_transport_age_sec` 和 `max_future_skew_sec` 负责拒绝刚刚收到的旧观测或异常未来时间；最终新鲜度仍由单调时间计算，避免服务端墙上时钟调整破坏窗口顺序。

流重连时清空姿态窗口和 episode，环境缓存可以保留，但仍必须重新通过因果性、新鲜度、设备绑定和 ROI 版本检查。主目标轨迹尚不可用时，弱光观测可以记录，依赖人体位置的水浸 ROI 交互必须是 `unavailable`。这里的“主目标可用”只表示当前专属视频流中的目标轨迹可用于计算，不代表完成了视觉身份核验。

## 6. 特征状态与计算规则

### 6.1 三态诊断

环境分支沿用现有分支状态：

| 状态 | 含义 | 典型原因 |
|---|---|---|
| `valid` | 输入完整且计算成功；分数 `0.0` 是合法的“未观察到该风险” | `dry`、正常照明、人在 ROI 外 |
| `unavailable` | 当前不能形成可信特征，不参与融合 | `no_binding`、`no_reading`、`stale_reading`、`sensor_fault`、`target_unbound`、`insufficient_ankle_quality`、`roi_version_mismatch` |
| `inference_error` | 输入原本可用，但算法代码发生非预期异常 | `environment_feature_failed` |

照度和每个水浸探头分别记录状态与原因；不能因为一个探头故障就把仍正常的照度通道一起作废。只有至少一个环境交互通道可计算时，整体环境交互才为 `valid`。

### 6.2 弱光分数

第一版采用可解释的分段线性映射：

```text
lux >= normal_lux      -> low_light_score = 0
lux <= severe_low_lux  -> low_light_score = 1
其他                   -> (normal_lux - lux) / (normal_lux - severe_low_lux)
```

结果限制在 `[0, 1]`。缺少标定版本、lux 非法、传感器故障或快照过期时，`low_light_score` 为不可用，而不是零。

### 6.3 水浸探头区域暴露

水浸探头只能说明探头附近检测到水。通道状态有效且为 `dry` 时，`water_exposure_score=0` 是有效零，不依赖人体位置。通道状态为 `water` 时，只有同时满足以下条件，才计算人员暴露：

1. 探头状态有效；
2. 摄像头、探头与 ROI 版本匹配；
3. 当前主目标绑定有效；
4. 最近 `roi_window_frames` 个姿态位于 `roi_max_span_sec` 内，其中至少 `roi_min_usable_frames` 帧有可用脚踝；
5. 至少 `roi_min_hits` 个可用帧中有一个脚踝点落入该探头 ROI。

ROI 命中按“帧”计数，不是把多帧中的左右脚踝点混在一起计数。窗口跨度超限或可用帧不足时结果为 `unavailable`。首版默认值为 3 帧窗口、至少 2 个可用帧且至少 2 帧命中，后续修改必须随配置版本记录。

```text
person_in_probe_zone = 0 or 1
water_presence_near_probe = 0 or 1
water_exposure_score = water_presence_near_probe * person_in_probe_zone
```

多人歧义、脚部遮挡、摄像头移动或 ROI 版本不匹配时拒绝计算。多个探头存在时先分别计算，再取有效探头中的最大暴露分，同时保留触发探头 ID 作为诊断证据。

### 6.4 人-环境交互

行为锚点只从当前 `fusion_mask=true` 的行为分支中选择：

```text
valid_behavior_scores = {
  gait_risk_score,
  sit_stand_risk_score,
  near_fall_event_score
} 中当前有效的分数

valid_behavior_scores 为空 -> environment_interaction_score = unavailable
否则 behavior_anchor = max(valid_behavior_scores)

light_interaction_score = low_light_score * behavior_anchor
water_interaction_score = water_exposure_score * behavior_anchor
environment_interaction_score = max(当前有效的 interaction score)
```

`fall_event_score` 和 `long_static_score` 不进入 `behavior_anchor`，避免环境分支介入 4 级强触发语义。行为分支有效且分数为零时，交互分为有效零；行为分支不可用时，不能用零代替。该交互分可以在 shadow 中完整记录，但 assist 还必须经过第 7.2 节的最小行为锚点门禁。

### 6.5 缓存与诊断

`FeatureAssembler` 当前按姿态窗口签名缓存结果。接入环境参数后，缓存签名必须同时包含：

```text
environment_device_id + boot_id + sequence + channel_status
+ calibration_version + roi_version
```

否则同一姿态窗口可能复用旧环境结果。环境字段采用以下固定落点：

| 字段 | 作用 |
|---|---|
| `features["environment_features"]` | 保存各通道分数、`behavior_anchor` 和最终交互分；不加入现有加权基线字段集合 |
| `features["environment_mask"]` | 保存照度、水浸暴露和交互分各自是否可用；不复用现有 `fusion_mask` |
| `branch_diagnostics["environment"]` | 保存模式、三态、原因、时间、设备、配置版本和耗时 |
| `AlgorithmEvent.metadata["environment"]` | 只在原事件已生成时保存紧凑、可序列化的环境证据 |

`branch_diagnostics["environment"]` 至少记录快照年龄、设备与序列、有效通道、lux、探头状态、ROI 判定、标定/ROI 版本和耗时。日志和接口不得包含 token、直播地址或原始视频帧。

## 7. Shadow 与 Assist 的输出语义

### 7.1 Shadow：只观察，不改决策

shadow 可以在内部 `FeatureSnapshot` 中增加环境特征和完整诊断，但必须满足以下回放不变量：

- 不把环境分支加入现有 `feature_coverage` 分母；
- 不改现有融合使用的 `fusion_mask`；环境可用性只记录在 `environment_mask`；
- 不修改顶层 `risk_factors`，因为它参与现有事件去重签名；
- 不修改 `model_version`、风险等级、建议动作或 episode 状态；
- 只在原有事件本来就会生成时，向 `AlgorithmEvent.metadata.environment` 附加紧凑诊断。

因此，基线和 shadow 在风险效果指标上按定义应完全相同。shadow 的用途是验证数据质量、环境特征正确性、系统延迟和误关联，不应被包装成一个效果更好的模型组。

### 7.2 Assist：受限增加分数

只有第 10 节门禁全部通过后，才允许启用：

```text
environment_contribution = environment_weight * environment_interaction_score
adjusted_score = clamp(base_risk_score + environment_contribution, 0, 1)
```

融合规则如下：

- `environment_weight` 只能由训练集/验证集确定，测试集只做一次冻结评估；
- 环境或行为锚点不可用时，`adjusted_score = base_risk_score`；
- `behavior_anchor < min_behavior_anchor` 时环境贡献强制为零；该阈值与权重一同冻结；
- 基线已经为 4 级时保持原 4 级结果，环境不得改写其触发原因；
- 基线低于 4 级时，可按既有分级边界重算，但结果最高为 3 级；
- 环境贡献为正时才增加交互型风险因子，不能把单独的低照度或探头有水写成行为风险；
- 启用 assist 后更新融合策略 `model_version`，确保结果可追溯；
- assist 影响普通风险 episode 属于预期行为，但跌倒强触发、静止确认和恢复条件仍使用原逻辑。

交互型风险因子根据形成行为锚点的分支映射，例如 `unstable_gait_under_low_light`、`sit_stand_difficulty_under_low_light`、`near_fall_under_low_light`、`unstable_gait_near_water` 和 `near_fall_near_water`。只有对应行为分支达到冻结的解释门槛时才能写入。`low_illumination` 和 `water_presence_near_probe` 只作为环境观测写入 metadata，不单独进入顶层风险因子。

### 7.3 连续 shadow 日志

普通 0 级观测不会产生风险回调，所以不能只依赖 `AlgorithmEvent.metadata` 收集实验数据。shadow 模式必须提供独立 JSONL 日志，每次完成特征装配时记录：

- 会话、摄像头、环境设备、`stream_epoch` 和姿态窗口 ID；
- 源 PTS、帧接收单调时间、环境接收单调时间和快照年龄；
- 行为分支分数、mask、环境特征、三态原因和配置版本；
- 基线预测结果，但不改变线上事件策略；
- 处理耗时和丢帧/过期诊断。

原始试验日志写入明确指定的数据路径，汇总指标、复现命令和失败案例写入 `reports/fall_risk/`。日志写入失败不得阻塞视频推理；必须计数并在会话诊断中暴露。

| 阶段 | 主要工作 | 必须产物 | 退出条件 |
|---|---|---|---|
| 0. 契约冻结 | 评审 schema、模式、状态原因、配置和日志字段 | schema 示例、配置示例、测试用例表 | 硬件端与算法端对字段、频率、重启和错误语义达成一致 |

| C. 交互特征 | lux 映射、ROI、脚踝稳定判定、交互公式和缓存失效 | 纯函数与 FeatureAssembler 测试 | ROI 外、dry、低质量脚踝、错误版本和无行为分支均符合第 6 节语义 |

| F. 受控启用 | 默认关闭的 assist 配置、回滚开关和真实视频烟测 | 可追溯策略版本、回滚记录 | 无环境单独 4 级、无 episode 语义回归、性能预算满足 |

## 10. 实验设计与 Assist 准入门禁

### 10.1 要回答的两个问题

1. 环境记录是否能稳定、正确地对齐到视频行为窗口？
2. 在无泄漏固定测试集上，环境交互是否比人体行为基线带来稳定收益，而不是增加偶然误报？

第一个问题由 shadow 回答；第二个问题由 base 与 assist 的离线对照回答。

### 10.2 配对采集矩阵

同一参与者、动作、机位和服装条件下，至少覆盖：

| 照明 | 探头 | 人员位置/行为 | 目的 |
|---|---|---|---|
| 正常 | dry | 正常与风险动作 | 人体基线 |
| 弱光 | dry | 同组动作 | 弱光交互 |
| 正常 | water | ROI 内外均采集 | 排除“探头有水就告警” |
| 弱光 | water | ROI 内外均采集 | 组合条件 |
| 正常/弱光 | 故障或断连 | 正常动作 | 缺失与降级 |
| 正常/弱光 | dry/water | 无人、多人歧义、脚踝遮挡 | 困难负样本 |

还应注入网络延迟、重复包、乱序包、设备重启和视频重连，验证时间与状态机边界。

不得让参与者在真实湿滑地面上行走。水浸条件使用探头电极受控触发或隔离容器；模拟踉跄、坐站困难和跌倒相关动作必须使用防护垫、扶手和保护人员。

### 10.3 数据与评估协议

- 环境真值至少标注照明条件、探头状态、人员是否进入探头 ROI、设备故障和网络注入条件；
- 风险效果继续使用现行事件标签契约，不能从传感器状态反推风险标签；
- 按参与者优先，其次按完整会话划分 train/validation/test，同一配对组不能跨 split；
- lux 阈值、ROI、行为门槛、环境权重和风险分级容差只能用 train/validation 确定；
- 测试集只在策略冻结后评估一次，并记录代码、配置、数据和 split hash；
- `P + E shadow` 只报告数据质量和系统指标；风险效果只比较冻结的 base 与 assist。

指标分为四组：

| 类别 | 指标 |
|---|---|
| 数据通路 | 接收率、重复/乱序率、过期率、故障识别率、端到端年龄分布 |
| 环境特征 | 弱光条件区分、dry/water 状态正确率、ROI 暴露 precision/recall、状态变化延迟 |
| 风险效果 | 事件 Recall、Precision、`FP/hour`、提前预警时间、校准误差和失败案例分布 |
| 工程性能 | 特征耗时 p50/p95、视频吞吐变化、日志丢弃数、内存上界和 2 小时稳定性 |

### 10.4 硬门禁

采集测试集前，必须在评估配置中冻结具体数值阈值和允许退化范围。无论阈值取值如何，以下条件不可放宽：

- `disabled` 与改动前基线的决策字段逐条一致；
- shadow 与 base 的决策字段、事件数量和 episode 转移逐条一致；
- 故障注入中的过期、乱序、非法和传感器故障全部被识别，不能进入有效融合；
- assist 不能由环境信号单独提高风险，不能使非 4 级结果变为 4 级；
- test 上主要召回指标不得超出预注册容差退化，`FP/hour` 和校准误差不得超出预注册上限；
- assist 至少在一个预注册主要指标上稳定优于 base，并提供按场景和参与者分层结果；
- 端到端延迟、内存和日志写入不破坏实时主链预算；
- 数据来源、标签、split、配置和代码版本可复现。

样本不足、只有模拟动作、split 无法按人隔离、收益只出现在 validation、误报明显增加或任何硬门禁失败时，结论都应是“保留 shadow，不启用 assist”。

## 12. 风险、降级与回滚

| 风险 | 影响 | 预防与降级 |
|---|---|---|
| 网络延迟使环境与视频错配 | 错误交互 | 因果查询、年龄上限、记录年龄分布；超限即 `unavailable` |
| 设备重启或旧包重放 | 新记录被拒或旧状态复用 | `boot_id + sequence`，重复幂等，回退拒绝 |
| 摄像头移动导致 ROI 失效 | 人员暴露误判 | ROI 绑定安装版本；版本不符立即不可用 |
| 脚踝遮挡或多人歧义 | 水浸区域误关联 | 3 帧质量门槛和主目标绑定；不满足即拒识 |
| 传感器故障被当作 dry/正常光 | 假低风险 | 通道级三态，故障不填零 |
| shadow 日志拖慢主链 | 延迟或积压 | 有界非阻塞写入、丢弃计数；风险推理优先 |
| assist 只对模拟数据有效 | 结论外推错误 | 固定 split、分层报告、真实连续数据不足时保持 shadow |
| 新 metadata 影响事件语义 | 回调数量或 episode 改变 | shadow 不改去重签名字段，并做逐条回放比较 |

运行时回滚只需把 `environment.mode` 改为 `disabled` 并重启服务；该操作不得要求修改会话请求、业务回调消费者或现有风险阈值。若 assist 出现异常，先回退 `shadow` 保留诊断，再定位问题，不继续使用环境贡献分。

## 13. 完成定义

只有同时满足以下条件，才能把本计划标记为完成：

- 环境 schema、配置和状态原因已经版本化并有文档；
- API、store、时间对齐、环境特征、shadow 日志和 assist 限制均有自动化测试；
- `disabled` 和 shadow 决策不变量通过固定回放；
- 完成安全的配对采集，数据与 split 可复现；
- 生成正式评估报告，明确记录通过项、失败项和不可声明结论；
- assist 若未通过全部门禁，默认配置仍为 `disabled` 或 `shadow`；
- 若 assist 通过，配置、权重、阈值、ROI、报告和 `model_version` 可互相追溯；
- 相关代码行为、接口、配置和限制同步更新模块 README、接口文档与当前任务清单。

“设备能上报”“界面能显示 lux”或“单个演示视频看起来有效”都不等于完成，也不能作为 assist 进入主路径的证据。
